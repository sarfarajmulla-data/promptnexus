# Caching

What is cached, where, for how long, and how it is invalidated. This app has an
unusually simple cache story because it has no server-side state — which removes
the entire class of bug where a cache serves one user's data to another.

---

## Layers

| Layer | What | Where | TTL | Invalidation |
|---|---|---|---|---|
| CDN | `public/index.html` | Edge | revalidate | Deploy (content changes) |
| CDN | UI JS/CSS (`/js/*`, `/app.js`, `/styles.css`) | Edge | 1 hour local; immutable with content hashing at scale | Deploy |
| CDN | `/engine/*` | Edge | 1 year, immutable | Deploy — the engine only changes when the repository does |
| Browser | Prompt library, settings, draft | `localStorage` | Until cleared | Explicit user action only |
| Browser | Engine modules | ES-module cache | Session | Page reload |
| Server | — | — | — | **Nothing is cached server-side** |

Configured in [`vercel.json`](../vercel.json):

```json
{ "source": "/engine/(.*)", "headers": [{ "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }] }
```

## Why the engine can be cached for a year

`public/engine/` is generated by `npm run build` and contains no user data and no
runtime state — it is a pure function library. The only way it changes is a new
deployment, which produces a new build output. The same applies to the UI assets
once they are content-hashed.

## What is never cached

| Never cached | Why |
|---|---|
| Every `/api/*` response | `Cache-Control: no-store` on all of them. Generation is input-dependent |
| The generated prompt in transit | It contains the user's own request; caching it at a shared layer would be a disclosure risk |
| Anything user-specific | There is nothing user-specific on the server. The library never leaves the browser |

The rule that would matter in a multi-user system — *any cache of tenant data must
include the tenant in the key* — is moot here because no such cache exists. It is
recorded so that if server-side storage is ever added, the rule is already written
down rather than rediscovered.

## Client-side state

| Key | Contents | Sensitivity |
|---|---|---|
| `promptforge.v1` | Settings, draft, library, onboarding state | The user's own text, on the user's own device |

Bound to `localStorage` deliberately:

- **No account, no sync, no server copy** — nothing to breach upstream.
- **Export exists** (`Settings → Data → Export JSON`) so the data is not locked in.
- **Delete is explicit** and requires confirmation; nothing is silently removed.
- **Private-mode failure is graceful**: if storage is unavailable the app runs in
  memory only and says nothing, because a blocked cache is not an error.

## Invalidation on write

There are no writes. Nothing to invalidate. That is the point.

## If server-side storage is added later

The rules that would then apply, recorded now:

1. Any cached response containing user data must include the user's identifier in
   the cache key — never a shared key.
2. Authenticated responses must be `private, no-store` at the CDN layer.
3. Invalidate on every write that affects the cached value; do not rely on TTL.
4. Add a bypass path for debugging and support.
5. Add a test proving two different users never receive each other's cached data.
